# Project external development tools

Click **External tools** beside the workspace folder below the message box. This opens the current project's tool permissions directly. Add the tool's installation folder; an executable path is optional and must stay inside that folder. **Verify access** reads the directory and executable metadata in the same Windows sandbox used by Claude; it does not start a build.

**Common tools** remembers tool names, installation folders and executable paths added on this computer. Each installation folder has one entry with its latest successfully added details. Existing grants populate the list automatically; removing project access keeps the remembered choice. **Add to this project** creates a separate grant for the current project after rechecking paths and project boundaries. Missing or changed paths need manual reauthorization. The catalog stays on this computer and does not grant access to other projects or devices.

This integration supports Claude Code on native Windows with the Codex Windows MXC runtime. It uses an existing workspace-terminal runtime or the registered native `codex.exe`. Other providers keep their native permissions. Directory grants do not enable networking or interactive editor automation.

The exact working folder is the scope; subfolders are separate projects. In the isolated terminal, installations are read-only. The project and `.starport-claude-runtime` are writable. Temporary, home, npm cache, AppData and LocalAppData folders are redirected into that project cache. A readable executable may still fail to start: complete Electron/Chromium and other application runtimes can require OS facilities unavailable inside MXC. **Verify access proves file reads only**, not startup or a valid build. No unrestricted retry occurs. Personal editor preferences and login files outside the grant are not exposed to the isolated terminal automatically.

## Host compatibility execution

> **Testing:** host compatibility execution and persistent applications have not been used in real work yet.

When a registered `.exe` cannot run in the sandbox, Claude can request `mcp__starport_external_tools__run`. The tool's **Host execution permission** defaults to **Ask every time**: Starport shows the executable, literal arguments, physical project directory and lifetime before launch. Choose **Always allow for this project** in External tools to remember your consent for this project's registered executable. Claude then launches it without repeated approvals. This setting stays on this computer, affects subsequent turns and is never copied to other projects by Common tools. Switch back to Ask every time to revoke future automatic launches. Existing running applications remain open until explicitly closed. Native Claude auto/bypass modes do not override these project settings.

This is an explicit exception: the application and its descendants run as the signed-in Windows user, with host filesystem, account/configuration and network access. Setting its working directory does **not** confine its file access. Approve only trusted programs and parameters; project scripts/plugins run by the program share these host rights. Ordinary Claude command execution remains in MXC. Adding a directory alone never authorizes unrestricted host execution.

The launcher runs only the project's registered `.exe`, without shell interpretation; paths/junctions are checked again after approval. The working directory must physically remain inside the project, including when a subfolder is a junction. Arguments use real absolute paths rather than PowerShell `StarPort:` virtual-drive paths. Exit codes default to `[0]`; tools with documented nonzero success codes can supply `successExitCodes`. Finite commands have a default timeout of 120 seconds, up to 15 minutes, and clean up their process tree on completion/cancellation. MCP results contain bounded output tails and the actual exit code to avoid inaccessible oversized-result spill files.

Set **`persistent: true`** when asking Claude to keep an editor or server running. Startup returns an application id; the process stays open across turns, Stop of a later conversation turn, and Starport restarts. Repeating the same tool/arguments/directory reuses that managed application. A Windows Job and independent owner retain its descendants even when an application launcher exits early. Logs are bounded on disk. Up to eight applications can run per project. Startup acknowledgement only proves that the process is alive, not that the project finished importing or is error-free.

Use `mcp__starport_external_tools__list` and `stop` to manage applications in subsequent turns, or **Persistent applications → Close application** in the project's External tools dialog. Save editor changes first: closing terminates the managed process tree. Control uses a unique job identity rather than a saved PID; other projects are excluded. Close live applications before removing their tool grant. Persistent metadata/logs live in `.data/external-applications`; these machine-local records are not portable grants. This opens the actual editor window; mouse/keyboard automation still requires a separate UI integration.

Grants live in the machine-local `.data/external-tools.json`, outside project files and shared memory. Do not transfer this as a portable permission grant. Moving a project requires adding its tools again. Physical targets are checked at grant time and before launches/commands; retargeted junctions require reauthorization. Broad drive, home, Starport and private-configuration roots are rejected.

Claude gets extra directories and Edit-deny rules. Its built-in command tools are disabled for these launches; ordinary commands use the SDK-hosted sandboxed MCP terminal, with the separately authorized host route above for complete applications. The terminal no longer depends on a per-turn stdio process/manifest. Private per-run settings retain owner proxy and browser/explicit MCP configuration, and are removed when the turn ends. Grant or execution-policy changes invalidate the native session fingerprint: the next turn receives the saved Starport conversation in a fresh native session. Chat history is retained.

Project grants cannot change or be verified during active conversation/workflow tasks. Load updates only when the server is idle; existing turns keep their original policy.

## Cocos Creator

Add a version folder such as `C:\DevTools\Cocos\Creator\3.8.8` and its `CocosCreator.exe`. Read engine files in the isolated terminal. Use host compatibility execution for complete builds; set the project's Host execution permission to Always allow to avoid repeated approvals. To keep the editor open, launch `args: ["--project", "<physical project path>"]` with `persistent: true`. No engine-specific launch flags are inserted by Starport.

Creator 3.8 uses `--project <project path> --build "platform=web-desktop;debug=true"`. Keep outputs/logs in the project. Cocos reports successful builds with exit code **36**. The game must already be a valid Cocos project; granting access does not convert it. See [Cocos command-line publishing](https://docs.cocos.com/creator/3.8/manual/en/editor/publish/publish-in-command-line.html).
